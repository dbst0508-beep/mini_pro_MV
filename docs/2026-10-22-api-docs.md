# Django API에 Swagger 문서 붙이기 (2026-10-22)

브랜치: `feature/api-docs`

> 한 줄 요약: `drf-spectacular`를 붙여서 Django API(게시물·댓글·좋아요)를 브라우저에서 읽고 직접 눌러 볼 수 있는 Swagger 화면(`/api/docs/`)을 만들었다. 그 화면에서 테스트하다가 **댓글 API가 URL의 게시물 번호를 무시하던 실제 버그**를 찾아 고치고 테스트를 추가했다.

---

## 1. 기술문서

### 1-1. Swagger가 뭐고 왜 붙였나

Swagger는 "이 서버에 어떤 주소가 있고, 무엇을 보내면 무엇이 돌아오는지"를 **웹 화면 한 장**으로 보여 주는 도구다. 화면에서 바로 요청을 보내 볼 수도 있다.

| | 설명 |
|---|---|
| 포트폴리오 | 코드를 열어 보지 않아도 API 구성이 한눈에 보임 |
| 개발 | 프론트 없이도 API를 눌러 보며 테스트할 수 있음 |
| 자동 생성 | 코드(시리얼라이저·뷰)를 읽어서 만들기 때문에, 문서를 따로 손으로 쓰지 않아도 코드와 어긋나지 않음 |

사용한 도구는 `drf-spectacular`다. DRF 코드를 읽어서 API 명세(OpenAPI)를 만들고, 그 명세를 Swagger 화면으로 보여 준다.

### 1-2. 바뀐 파일

| 파일 | 구분 | 내용 |
|---|---|---|
| `pyproject.toml`, `uv.lock` | 수정 | `drf-spectacular` 추가 |
| `config/settings.py` | 수정 | 앱 등록, `REST_FRAMEWORK` 설정, `SPECTACULAR_SETTINGS`(제목·설명·버전, 요청/응답 명세 분리) |
| `config/urls.py` | 수정 | `/api/schema/`, `/api/docs/` 주소 추가 |
| `posts/views.py` | 수정 | 그룹(태그)·한 줄 설명, 파일 업로드 문서화, 좋아요 응답 설명, **댓글 단건 API 버그 수정** |
| `posts/tests.py` | 수정 | 버그 재발 방지 테스트 1개 추가 |

### 1-3. 새로 생긴 주소

| 주소 | 용도 |
|---|---|
| `/api/docs/` | Swagger 화면 (사람이 보는 곳) |
| `/api/schema/` | API 명세 원본 데이터 (Swagger 화면이 이걸 읽어서 그림을 그림) |

### 1-4. 문서에 들어간 API와 빠진 API

| 포함 | 이유 |
|---|---|
| 게시물 목록·작성 | DRF 뷰라서 자동으로 읽힘 |
| 댓글 목록·작성·단건 조회·수정·삭제 | 같음 |
| 좋아요 토글 | 같음 (응답 모양은 직접 설명을 붙임) |

| 제외 | 이유 |
|---|---|
| AI 분석 관련 주소(`/analysis/...`) | DRF가 아니라 일반 Django 뷰라서 자동 생성 대상이 아님. AI 분석 서버 `cv_service`는 자기 Swagger(`http://localhost:8001/docs`)가 따로 있음 |
| 피드·상세·로그인 등 화면 주소 | HTML을 돌려주는 화면이지 API가 아님 |

### 1-5. 화면 구성

Swagger 화면은 API를 세 그룹으로 묶어 보여 준다.

| 그룹 | 들어 있는 API |
|---|---|
| 게시물 | 목록 조회, 작성 |
| 댓글 | 목록 조회, 작성, 단건 조회, 전체 수정(PUT), 부분 수정(PATCH), 삭제 |
| 좋아요 | 토글 (누르면 201 "추가됨", 다시 누르면 200 "취소됨") |

### 1-6. Swagger에서 로그인하는 법

이 프로젝트는 세션 로그인이다. 같은 브라우저에서 `http://localhost:8000/login/`으로 먼저 로그인한 뒤 `/api/docs/`를 열면, 그 로그인 상태로 요청이 나간다. (Swagger 화면에서 따로 로그인 버튼을 누르지 않는다.)

### 1-7. 이번에 고친 버그

| | 수정 전 | 수정 후 |
|---|---|---|
| `PUT /api/posts/2/comments/1/` (1번 댓글은 1번 게시물 것) | 200, 1번 댓글이 **수정됨** | 404 |
| 의미 | URL의 게시물 번호를 아예 무시하고 댓글 번호만 봄 | URL의 게시물 번호에 속한 댓글만 대상으로 삼음 |

조회·수정·삭제 모두 같은 문제였다.

## 2. 클래스·함수 단위 코드리뷰

### `config/settings.py`

| 항목 | 역할 |
|---|---|
| `INSTALLED_APPS`의 `'drf_spectacular'` | Django에게 "이 도구를 쓴다"고 알리는 등록 |
| `REST_FRAMEWORK['DEFAULT_SCHEMA_CLASS']` | DRF가 명세를 만들 때 쓸 도구를 drf-spectacular로 지정 |
| `SPECTACULAR_SETTINGS` | Swagger 화면 맨 위의 제목·설명·버전 |
| `SERVE_INCLUDE_SCHEMA: False` | `/api/schema/` 주소 자체가 Swagger 목록에 끼어드는 것을 막음 |
| `COMPONENT_SPLIT_REQUEST: True` | 요청용·응답용 명세를 따로 만듦. 응답에서는 이미지가 "주소"이지만 요청에서는 "파일"이라서, 나누지 않으면 요청 칸도 주소 입력칸으로 보임 |

### `config/urls.py`

| 항목 | 역할 |
|---|---|
| `SpectacularAPIView` | 명세 데이터를 내려주는 뷰 (`name="schema"`) |
| `SpectacularSwaggerView(url_name="schema")` | Swagger 화면을 그리는 뷰. "명세는 `schema`라는 이름의 주소에서 가져와라"라는 뜻 |

### `posts/views.py`

| 항목 | 역할 |
|---|---|
| `@extend_schema_view(get=..., post=...)` | 클래스 하나에 GET/POST 같은 메서드별 설명을 한꺼번에 붙이는 데코레이터 |
| `extend_schema(tags=, summary=)` | 해당 메서드를 어느 그룹에 넣을지, 한 줄 제목은 무엇인지 |
| `request={"multipart/form-data": PostSerializer}` | 게시물 작성 요청을 "파일 업로드 형식"으로만 문서화 → Swagger에 **파일 선택 버튼**이 나옴 |
| `swagger_fake_view` 검사 | 문서를 만드는 중에는 실제 URL 값(`post_id`)이 없어서 에러가 나는데, 그때는 빈 결과를 돌려줘서 피함 |
| `CommentDetailAPIView.get_queryset` | **이번 버그 수정 지점.** "URL의 게시물에 속한 댓글"만 대상으로 삼도록 범위를 좁힘 |
| `LikeToggleResponseSerializer` (`inline_serializer`) | 좋아요 응답 `{liked, like_count}`의 모양을 문서용으로 즉석에서 정의 |
| `LikeToggleAPIView.post`의 `@extend_schema` | 요청 본문 없음, 201/200 응답의 의미를 문서에 적음 |

### `posts/tests.py`

| 항목 | 역할 |
|---|---|
| `test_comment_of_other_post_is_not_found` | 다른 게시물 번호 + 원래 댓글 번호 조합으로 조회·수정·삭제하면 모두 404이고, 댓글은 그대로인지 확인 |

## 3. 한 줄 한 줄 주석 코드

### 3-1. `config/settings.py` (추가된 부분)

```python
INSTALLED_APPS = [
    # ... 기존 앱들 ...
    'rest_framework',
    'drf_spectacular',                                       # API 명세를 자동으로 만들어 주는 앱 (Swagger 화면의 재료를 생산)
]

# API 문서(Swagger) 설정
REST_FRAMEWORK = {                                           # DRF 전체 설정 묶음
    'DEFAULT_SCHEMA_CLASS': 'drf_spectacular.openapi.AutoSchema',  # DRF가 API 명세를 만들 때 drf-spectacular의 방식을 쓰도록 지정
}

SPECTACULAR_SETTINGS = {                                     # drf-spectacular 전용 설정 묶음
    'TITLE': 'mom vision API',                               # Swagger 화면 맨 위에 표시될 제목
    'DESCRIPTION': '패션 SNS 게시물·댓글·좋아요 API. AI 분석 파이프라인은 cv_service(FastAPI)의 /docs를 참고.',  # 제목 아래 설명
    'VERSION': '1.0.0',                                      # API 버전 표시
    'SERVE_INCLUDE_SCHEMA': False,                           # 명세 데이터 주소(/api/schema/) 자체는 Swagger 목록에 나타나지 않게 함
    'COMPONENT_SPLIT_REQUEST': True,                         # 요청용/응답용 명세를 따로 만듦 → 이미지 칸이 "주소 문자열"이 아니라 "파일 선택 버튼"으로 나옴
}
```

### 3-2. `config/urls.py` (추가된 부분)

```python
from drf_spectacular.views import SpectacularAPIView, SpectacularSwaggerView  # 명세 데이터 뷰, Swagger 화면 뷰

urlpatterns = [
    # ... 기존 주소들 ...
    path("api/schema/", SpectacularAPIView.as_view(), name="schema"),  # API 명세 데이터를 내려주는 주소 (화면을 그리는 재료)
    path("api/docs/", SpectacularSwaggerView.as_view(url_name="schema"), name="swagger-ui"),  # Swagger 화면. url_name="schema"는 위 주소에서 명세를 가져오라는 뜻
]
```

```python
from drf_spectacular.utils import extend_schema, extend_schema_view, inline_serializer, OpenApiResponse  # Swagger 문서에 설명을 덧붙이는 도구들
from rest_framework import serializers                                # inline_serializer로 응답 모양을 만들 때 필드 타입을 쓰기 위해 불러옴

@extend_schema_view(                                                  # 이 클래스의 메서드(GET/POST)마다 Swagger 설명을 따로 붙이는 데코레이터
    get=extend_schema(tags=["게시물"], summary="게시물 목록 조회"),           # GET 요청: "게시물" 그룹에 묶고, 한 줄 설명 표시
    post=extend_schema(tags=["게시물"], summary="게시물 작성 (로그인 필요)", request={"multipart/form-data": PostSerializer}),  # POST 본문을 파일 업로드(multipart) 형식으로만 문서화 → 파일 선택 버튼이 나옴
)
class PostListCreateAPIView(generics.ListCreateAPIView):
    ...  # 본문은 기존과 같음
```

class CommentListCreateAPIView(generics.ListCreateAPIView):

class CommentDetailAPIView(generics.RetrieveUpdateDestroyAPIView):
    serializer_class = CommentSerializer  # 응답/수정에 CommentSerializer를 그대로 사용
    permission_classes = [IsOwnerOrReadOnly]  # 조회는 누구나, 수정/삭제는 작성자만
    lookup_url_kwarg = "comment_id"  # URL에서 댓글을 찾을 때 "comment_id" 값을 사용 (기본값은 "pk")
    def get_queryset(self):                                            # 이 API가 다룰 댓글의 범위를 정하는 함수 (요청마다 호출됨)
        if getattr(self, "swagger_fake_view", False):                  # Swagger 문서를 만드는 중이면
            return Comment.objects.none()                              # 빈 결과를 돌려줘서 self.kwargs["post_id"] 에러를 피함

    def test_comment_of_other_post_is_not_found(self):  # URL의 게시물 번호와 댓글의 실제 게시물이 다르면 404여야 하는지 확인
        other_post = Post.objects.create(user=self.user, image="posts/test2.jpg", caption="다른 게시물")  # 댓글이 하나도 없는 다른 게시물
        wrong_url = f"/api/posts/{other_post.id}/comments/{self.comment.id}/"  # 다른 게시물 번호 + 원래 댓글 번호: 맞지 않는 조합
        self.client.force_authenticate(user=self.user)  # 댓글 작성자 본인으로 로그인 (권한이 아니라 "조합" 문제만 보기 위해)

        self.assertEqual(self.client.get(wrong_url).status_code, status.HTTP_404_NOT_FOUND)  # 조회해도 404여야 함
        response = self.client.patch(wrong_url, {"content": "엉뚱한 곳에서 수정"})  # 이 주소로 수정을 시도
        self.assertEqual(response.status_code, status.HTTP_404_NOT_FOUND)  # 수정도 404로 막혀야 함
        self.assertEqual(self.client.delete(wrong_url).status_code, status.HTTP_404_NOT_FOUND)  # 삭제도 404로 막혀야 함

        self.comment.refresh_from_db()  # DB 최신 상태 다시 불러오기
        self.assertEqual(self.comment.content, "원본 댓글")  # 내용이 바뀌지 않고 그대로여야 함
        self.assertEqual(Comment.objects.count(), 1)  # 삭제되지 않고 그대로 1개 남아 있어야 함

## 4. 복습

### 문서를 자동으로 만든다는 건
- 코드(시리얼라이저의 필드, 뷰의 종류)를 읽어서 "이 주소는 이런 걸 받고 이런 걸 돌려준다"를 **프로그램이 알아서 정리**한다.
- 자동이라 못 읽는 부분(파일 업로드 형식, 직접 만든 응답 모양)은 `extend_schema`로 설명을 **보충**한다.

### 직접 눌러 보는 문서의 장점
- 문서를 보려고 눌러 본 것인데 **버그가 발견**됐다. 문서는 읽는 것이고, 눌러 보는 것은 테스트다.
- 이번에는 "게시물 2번 주소로 1번 댓글이 수정된다"는 것을 화면에서 직접 보고 알았다.

### 댓글 번호는 게시물별 순번이 아니다
- `comment_id`는 DB 전체에서 매겨지는 **고유 번호**다. 게시물마다 1, 2, 3…으로 다시 시작하지 않는다.
- 지운 댓글의 번호는 다시 쓰이지 않는다. 그래서 번호가 중간에 비어 있어도(예: 1, 3, 4) 정상이다.

### 조회 범위를 좁힌다는 것 (`get_queryset`)
- "이 API가 다룰 수 있는 데이터 전체"를 정하는 곳이 `queryset`이다. 여기서 범위를 좁히면 범위 밖 데이터는 **없는 것처럼 404**가 된다.
- 권한(403 "너는 안 돼")과 범위(404 "그런 건 없어")는 다른 문제다.

### 새 기능을 고치면 테스트도 같이
- 버그를 고치기 **전에** 테스트를 먼저 만들어 실패(`200 != 404`)하는 것을 확인했고, 고친 뒤 통과하는 것을 확인했다. 그래야 테스트가 진짜로 그 버그를 잡는다고 믿을 수 있다.

### Docker 코드 반영
- 이 프로젝트의 Docker 이미지는 코드를 이미지 안에 **복사해서** 굳힌다. 코드를 고친 뒤에는 `docker compose build` 후 `docker compose up -d`를 해야 반영된다.

## 5. 트러블슈팅

### 5-1. 댓글 API가 URL의 게시물 번호를 무시하고 있었다

| | 내용 |
|---|---|
| 증상 | Swagger에서 `PUT /api/posts/2/comments/1/`을 보냈더니 200이 오고, 1번 게시물에 달린 1번 댓글이 수정됨 |
| 원인 | `CommentDetailAPIView`의 `queryset`이 `Comment.objects.all()`이라 전체 댓글이 대상이었고, 댓글을 찾는 조건은 `comment_id` 하나뿐이었음. URL의 `post_id`는 받아 놓고 쓰지 않았음 |
| 해결 | `queryset=` 줄을 지우고 `get_queryset`을 만들어 `Comment.objects.filter(post_id=self.kwargs["post_id"])`로 범위를 좁힘 |
| 재발 방지 | `test_comment_of_other_post_is_not_found` 테스트 추가 (고치기 전에는 실패, 고친 뒤 통과). posts 테스트 17개 전부 통과 |
| 교훈 | 화면에서 직접 눌러 보는 문서가 코드 리뷰로 놓친 버그를 찾아 줌 |

### 5-2. 문서 생성 중 `post_id` 때문에 에러가 날 수 있음

| | 내용 |
|---|---|
| 증상 | 명세를 만드는 중에 `self.kwargs["post_id"]`를 읽는 `get_queryset`이 경고/에러를 냄 |
| 원인 | 명세를 만들 때는 진짜 요청이 아니라서 URL에서 온 `post_id`가 없음 |
| 해결 | `getattr(self, "swagger_fake_view", False)`가 참이면 `Comment.objects.none()`을 돌려줌 (두 댓글 뷰 모두) |
| 확인 | `spectacular --file schema.yml --validate` 실행 시 경고 없음 |

### 5-3. 게시물 작성 화면에서 `image`가 파일 선택이 아니라 글자 입력칸으로 보임

| | 내용 |
|---|---|
| 증상 | `POST /api/posts/`의 `image`가 `string($uri)` 입력칸으로 나와서 파일을 올릴 수 없음 |
| 원인 | 요청 본문의 형식이 여러 개(JSON, 폼, 파일 업로드)로 문서화되어, Swagger가 기본으로 보여 주는 JSON 형식에서는 이미지가 "주소 글자"로 표현됨. 또 요청용·응답용 명세가 하나로 합쳐져 있어서, 응답에서 이미지가 "주소(URI)"인 모양이 요청 칸에도 그대로 쓰임 |
| 해결 | 두 가지를 같이 적용함. ① `settings.py`의 `SPECTACULAR_SETTINGS`에 `'COMPONENT_SPLIT_REQUEST': True` 추가 → 요청용·응답용 명세를 따로 만듦. ② `extend_schema(post=..., request={"multipart/form-data": PostSerializer})` → 게시물 작성 요청을 파일 업로드 형식으로만 문서화 |
| 확인 | 파일 선택 버튼이 나오고, Swagger에서 실제로 게시물이 올라가는 것까지 확인 |
| 참고 | 두 설정을 함께 적용한 뒤 확인해서, 둘 중 어느 쪽이 결정적이었는지는 따로 떼어 검증하지 않았음 |

### 5-4. 댓글 단건 주소가 404로 나옴 (버그 아님)

| | 내용 |
|---|---|
| 증상 | `/api/posts/1/comments/2/`가 404 |
| 원인 | 2번 댓글을 지운 상태였음. 댓글 번호는 DB 전체의 고유 번호이고 지워도 재사용되지 않으며, 새로 만든 댓글은 3, 4, 5…번이 붙음 |
| 확인 | `select id, post_id, content from posts_comment order by id`로 실제 존재하는 번호 확인 |
| 교훈 | 404가 나오면 코드를 의심하기 전에 그 번호가 DB에 있는지부터 확인 |

### 5-5. Docker에서 코드를 고쳤는데 화면에 반영되지 않음

| | 내용 |
|---|---|
| 증상 | 설정·뷰를 고쳤는데 `http://localhost:8000/api/docs/`가 그대로임 |
| 원인 | 코드가 이미지 안에 복사되어 있어서, 이미지를 다시 만들기 전까지는 옛 코드로 실행됨 |
| 해결 | `docker compose build` → `docker compose up -d` |
