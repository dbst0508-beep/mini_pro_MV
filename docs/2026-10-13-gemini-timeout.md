# Gemini 응답 지연 대비 (구글이 느려도 분석은 끝나게) — 2026-10-13

## 1. 기술문서

### 한 줄 요약
Gemini가 답을 늦게 주거나 안 줄 때, 분석 전체가 5분 뒤 "실패"로 끝나던 것을 **약 1분 안에 "완료"(탐지 결과 + 안내 문구)** 로 끝나게 바꿨습니다.

### 무엇이 문제였나
서버 4개를 켜고 분석을 요청했더니 5분 뒤 "분석 실패"가 떴습니다. 처음에는 노트북 사양을 의심했지만 원인은 다른 곳에 있었습니다.

cv_service는 요청 하나를 이렇게 차례로 처리합니다.

```
① 탐지 → ② 라벨링 → ③ Gemini 호출 → ④ Django로 결과 전달
```

단계별로 시간을 재 보니 다음과 같았습니다.

| 단계 | 걸린 시간 | 어디서 도는가 |
|---|---|---|
| 모델 불러오기 | 8초 | 내 노트북 |
| 탐지 | 1초 | 내 노트북 |
| 라벨링 | 1초 | 내 노트북 |
| **Gemini 호출** | **123초** | **구글 서버** |

노트북에서 도는 부분은 전부 합쳐 10초였고, 느린 것은 구글의 답을 기다리는 시간뿐이었습니다. 구글이 돌려준 에러는 `503 ... currently experiencing high demand`(지금 요청이 몰려서 못 받는다)였습니다.

### 왜 "실패"까지 갔나
두 가지가 겹쳤습니다.

1. **기다리는 시간에 제한이 없었다.** Gemini가 답을 줄 때까지 무한정 기다렸습니다.
2. **라이브러리가 몰래 재시도를 하고 있었다.** `google-genai`는 503을 받으면 알아서 3번 더 요청합니다. 우리가 한 번 호출하면 실제로는 최대 4번 요청이 나갑니다.

구글이 요청 하나를 약 30초 붙잡았다가 503을 돌려주니, 4번 × 30초 = 약 2분이 걸렸습니다. 서버 안에서는 이보다 더 길어져 Celery의 제한 시간(300초)을 넘겼고, 멀쩡히 끝난 탐지 결과까지 통째로 버려졌습니다.

### 해결: 두 가지 제한
| 설정 | 값 | 뜻 |
|---|---|---|
| `LLM_TIMEOUT` | 30 | 요청 **한 번**을 기다리는 최대 시간(초) |
| `LLM_RETRY_ATTEMPTS` | 1 | 실패했을 때 다시 시도하는 횟수 (기본 3 → 1) |

가장 오래 걸리는 경우는 `30초 × 2번 + 쉬는 시간 몇 초 ≈ 64초`입니다. Celery 제한(300초)보다 훨씬 짧아서, Gemini가 아무리 느려도 분석이 통째로 실패하지 않습니다.

제한에 걸리면 에러가 나고, 이미 만들어 둔 `except`가 받아서 탐지 결과와 FashionCLIP 라벨은 살린 채 대체 문구로 마무리합니다. 이 대체 경로는 비전 LLM을 붙일 때 만들어 둔 것이고, 이번 작업은 그 경로로 **제때 들어가게** 만든 것입니다.

### 바뀐 결과 (Gemini가 응답하지 않을 때)
| | 변경 전 | 변경 후 |
|---|---|---|
| 기다리는 시간 | 5분 | 약 1분 |
| 화면 | 분석 실패 | 분석 완료 |
| 사진 위 박스·아이템 카드 | 없음 | 나옴 (FashionCLIP 라벨) |
| 스타일 해석 | 없음 | "스타일 해석을 생성하지 못했습니다..." |

### 시간 제한의 층 (바깥에서 안쪽으로)
| 누가 | 무엇을 기다리나 | 제한 |
|---|---|---|
| 상태 조회 API | 분석이 끝나기를 | 6분 |
| Celery task | cv_service의 응답을 | 300초 |
| cv_service | Gemini의 응답을 | 약 64초 (이번에 추가) |

안쪽 제한이 바깥 제한보다 짧아야 합니다. 그래야 안쪽에서 먼저 포기하고 "여기까지는 됐다"는 결과를 바깥으로 넘길 수 있습니다. 이전에는 맨 안쪽에 제한이 없어서 바깥 제한이 먼저 터졌습니다.

### 변경 파일
| 파일 | 내용 |
|---|---|
| `cv_service/app/interpretation.py` | `LLM_TIMEOUT`, `LLM_RETRY_ATTEMPTS` 추가, 클라이언트에 재시도 옵션, 호출에 `timeout` |
| `README.md` | cv_service 설명에 응답 지연 대비 항목 추가 |

## 2. 클래스·함수 단위 코드리뷰

### `LLM_TIMEOUT = 30` — 왜 30초인가
평소 Gemini는 3초 안에 답합니다. 30초는 그 10배라서 정상 응답을 잘못 끊을 일이 없고, 사용자가 화면 앞에서 기다릴 만한 한계이기도 합니다. 숫자를 코드 중간에 그냥 쓰지 않고 이름을 붙여 파일 위쪽에 둔 것은, 나중에 값을 바꿀 때 찾기 쉽게 하기 위해서입니다.

### `LLM_RETRY_ATTEMPTS = 1` — 왜 0이 아닌가
서버 혼잡은 보통 잠깐이라, 한 번 더 두드리면 성공하는 경우가 있습니다. 재시도를 아예 없애면 잠깐의 혼잡에도 해석이 빠집니다. 반대로 기본값 3은 최악의 경우 2분이 넘습니다. 1번은 그 사이의 절충입니다.

**살펴볼 점:** 이 값이 뜻하는 것이 "재시도 횟수"라는 것은 라이브러리 코드를 직접 읽고, 실행 시간(64초 ≈ 30초 × 2)으로 확인한 것입니다. 라이브러리 문서에는 "첫 요청을 포함한 전체 횟수"라고 적혀 있어서, 라이브러리 버전이 바뀌면 동작이 달라질 수 있습니다. 버전을 올린 뒤에는 시간을 다시 재 보는 것이 안전합니다.

### `client = genai.Client(http_options=...)` — 재시도는 클라이언트에 설정
재시도 횟수는 호출할 때마다 정하는 것이 아니라, 접속 준비물인 `client`를 만들 때 한 번 정합니다. 이 `client`는 서버가 뜰 때 한 번만 만들어지고 모든 요청이 함께 씁니다.

### `timeout=LLM_TIMEOUT` — 제한 시간은 호출에 설정
제한 시간은 `interactions.create(...)`를 부를 때 넘깁니다. 이 값은 **요청 한 번당** 제한입니다. 재시도까지 합친 전체 시간이 아니라는 점이 이번 작업에서 가장 헷갈린 부분입니다(트러블슈팅 2번).

### `except Exception` — 이번엔 손대지 않은 핵심
시간 초과든 503이든 모두 이 `except`로 들어와 `([], FALLBACK_INTERPRETATION)`을 돌려줍니다. 새 코드를 한 줄도 추가하지 않고 기존 대체 경로를 그대로 쓴 것입니다. "뭐가 터져도 탐지 결과는 살린다"는 처음 설계가 이번에 실제로 쓰였습니다.

### 남아 있는 약점
- Gemini가 느릴 때 사용자는 여전히 최대 1분을 기다립니다. 탐지 결과를 먼저 보여 주고 해석은 나중에 채우는 방식이면 더 좋지만, 구조를 크게 바꿔야 합니다.
- 해석이 빠진 분석은 "완료"로 저장되므로, 구글이 정상으로 돌아와도 자동으로 다시 채워지지 않습니다. 사용자가 다시 분석을 요청해야 합니다.
- 실패 원인은 여전히 `print`로만 남습니다.

import io  # 파일로 저장하지 않고 메모리 안에서 이미지를 JPEG로 변환할 때 씀

client = genai.Client(  # 환경변수 GEMINI_API_KEY를 자동으로 읽어서 접속 준비 (서버 뜰 때 한 번만 실행)

### `interpret_style` (전체)

```python
def interpret_style(image, items):
    """사진 + 탐지 결과를 Gemini에 보내서 (스타일 비율 리스트, 해석 텍스트)를 돌려받고, 아이템 라벨도 갱신함"""
    try:  # 아래에서 뭐가 잘못되든 except로 넘어가게 감쌈
        interaction = client.interactions.create(  # Gemini에 요청 보내기
            model=MODEL_NAME,  # 어떤 모델에게 물을지
            input=[  # 보낼 내용 (글 + 사진)
                {"type": "text", "text": build_prompt(items)},  # 글로 된 요청
                {"type": "image", "data": image_to_base64(image), "mime_type": "image/jpeg"},  # 사진
            ],
            response_format={  # "자유로운 글 말고, 이 모양의 JSON으로만 답해"라고 강제
                "type": "text",  # 답은 글자 형태
                "mime_type": "application/json",  # 그 글자는 JSON 형식
                "schema": StyleAnalysisResult.model_json_schema(),  # JSON의 구체적인 모양
            },
            timeout=LLM_TIMEOUT,  # ★ 이 시간 안에 답이 안 오면 에러 → 아래 except가 받음
        )
        result = StyleAnalysisResult.model_validate_json(interaction.output_text)  # JSON 글자 → 파이썬 객체 (모양이 틀리면 에러)
    except Exception as error:  # 시간 초과, 서버 혼잡(503), 한도 초과, 이상한 응답 등 뭐가 터져도
        print(f"[interpret_style] LLM 호출 실패: {error}")  # 서버 로그에 원인만 남기고
        return [], FALLBACK_INTERPRETATION  # 탐지 결과는 살릴 수 있게 빈 값으로 돌려줌

    apply_labels(items, result.item_labels)  # 성공했을 때만 실행됨 → 실패 시엔 FashionCLIP 라벨이 그대로 남음
    return normalize_scores(result.style_scores), result.interpretation  # (정리된 스타일 비율, 해석 텍스트)
```

## 4. 복습 (이번에 새로 익힌 개념)

### 느린 것과 멈춘 것을 구분하려면 단계별로 시간을 잰다
"너무 오래 걸린다"는 느낌만으로는 원인을 알 수 없습니다. 처음에는 노트북 사양을, 그다음에는 메모리 부족을 의심했지만 둘 다 틀렸습니다. 각 단계 앞뒤로 시각을 찍어 숫자로 보니 한 번에 범인이 나왔습니다. 추측이 두 번 틀린 뒤에야 재 본 것이 이번의 반성할 점입니다.

### `free -h` 읽는 법
메모리 상태를 보는 명령입니다. `available`이 지금 쓸 수 있는 여유이고, `Swap`의 `used`가 크면 메모리가 모자라 디스크를 빌려 쓰는 중이라는 뜻입니다. 이번에는 여유 4GB, 스왑 거의 0이어서 메모리는 원인이 아니었습니다.

### HTTP 상태 코드로 "누구 잘못인지" 가린다
| 코드 | 뜻 | 누구 문제 |
|---|---|---|
| 401 / 403 | 키가 틀렸거나 권한이 없음 | 내 쪽 (API 키) |
| 429 | 한도를 넘게 요청함 | 내 쪽 (사용량) |
| 503 | 서버가 지금 못 받음 | 상대 쪽 (구글) |

이번에 "API 키 문제인가?" 하는 의문이 들었지만 503이라 키 문제가 아니었습니다. 4로 시작하면 요청한 쪽, 5로 시작하면 서버 쪽 문제라고 기억하면 됩니다.

### 라이브러리는 말없이 재시도한다
많은 API 라이브러리는 일시적인 오류에 자동으로 다시 시도합니다. 편리하지만, 한 번 호출한 것이 여러 번 요청으로 나가서 시간이 몇 배로 늘어납니다. 사용량 화면의 "요청 11건, 503 오류 8건"은 실패한 호출 2번 × 4회 요청이었습니다. 숫자가 이상하게 많으면 재시도를 의심합니다.

### 제한 시간은 "한 번당"인지 "전체"인지 확인한다
`timeout=30`은 요청 한 번당 제한이었습니다. 재시도가 3번이면 전체로는 2분이 될 수 있습니다. 전체 시간을 묶으려면 **한 번당 제한 × 시도 횟수**를 같이 정해야 합니다.

### 안쪽 제한은 바깥 제한보다 짧게
기다림이 여러 겹일 때(Celery → cv_service → Gemini), 안쪽이 먼저 포기해야 "되는 데까지 한 결과"를 바깥으로 넘길 수 있습니다. 바깥이 먼저 포기하면 안쪽에서 해 둔 일이 전부 버려집니다.

### 부분 실패는 전체 실패로 만들지 않는다
식당에서 디저트 재료가 떨어졌다고 다 만든 메인 요리까지 안 내보내지는 않습니다. 외부 서비스 하나가 안 될 때, 되는 부분은 보여 주고 안 되는 부분만 알리는 것이 낫습니다.

### 코드로 고칠 수 있는 것과 없는 것
구글이 붐비는 것은 우리가 고칠 수 없습니다. 고칠 수 있는 것은 "그때 사용자가 무엇을 보는가"입니다. 이번 수정은 Gemini를 성공시키는 것이 아니라, 실패했을 때의 결과를 바꾼 것입니다.

## 5. 트러블슈팅

### 1) 분석이 5분 뒤 실패 — 노트북 사양 문제로 오해
- **증상:** 분석 요청 후 5분 뒤 "분석 실패". Celery 로그에 `Read timed out. (read timeout=300)`.
- **잘못 짚은 원인:** 노트북 사양 → 메모리 부족 → 모델 불러오기 순으로 의심했으나 모두 아니었음 (`free -h`로 여유 4GB 확인, uvicorn 로그로 모델이 이미 올라온 것 확인, 모델 불러오기 8초).
- **진짜 원인:** 단계별 시간 측정 결과 Gemini 호출만 123초. 구글 서버 혼잡(503).
- **해결:** 요청 한 번당 30초 제한 + 재시도 1회.

### 2) `timeout=30`을 넣었는데도 119초가 걸림
- **증상:** 제한 시간을 넣은 뒤 다시 재도 119초, 에러는 여전히 503.
- **원인:** 라이브러리가 503을 받으면 3번 더 재시도함. 구글이 매번 30초가 되기 직전에 503을 돌려줘서 한 번당 제한에는 걸리지 않고, 4번이 차례로 쌓임.
- **확인 방법:** 설치된 라이브러리 코드에서 재시도 설정을 직접 찾아 읽음. 사용량 화면의 503 오류 8건(= 호출 2번 × 4회)과도 일치.
- **해결:** 클라이언트를 만들 때 재시도를 1회로 제한.

### 결과 검증
